# WO 10.15 — Midtrans Resume Payment Architecture (ANALISIS EVIDENCE-BASED)

## Ringkasan / Conclusion

Menentukan mekanisme yang benar untuk **Guest → Resume Payment → tetap menggunakan
Order A** (order `pending`/`unpaid` yang sudah punya Snap transaction).

**Kesimpulan:** **OPTION A (reuse Snap token via `window.snap.pay`) adalah satu-satunya
mekanisme resmi yang selalu valid selama token hidup** — dibuktikan end-to-end: token
dipakai ulang untuk membuka kembali halaman pembayaran DAN pembayaran bisa
DISELESAIKAN sampai `capture` (order D jadi `paid`). OPTION B (Snap token baru untuk
order_id yang sama) hanya valid selama **belum ada payment method yang dipilih** dan
membatalkan token lama; begitu ada transaksi `pending` → Midtrans menolak dengan
`transaction_details.order_id sudah digunakan`. OPTION C (one-to-many order_id dengan
suffix) adalah rekomendasi resmi Midtrans untuk multi-attempt, tetapi butuh perubahan
mapping callback.

Tidak ada kode yang diubah. Tidak ada commit/push/deploy. Semua eksperimen di
sandbox. Order A/B/C/D dibiarkan sebagai bukti.

## STEP 3 — DOKUMEN RESMI MIDTRANS

Sumber: `https://docs.midtrans.com/docs/snap-advanced-feature` (diakses WO 10.15)

1. **Snap token default expiry 24 jam** (dapat dikustomisasi).
2. **Customer dapat membayar ulang order yang sama** → simpan Snap token, panggil lagi
   `window.snap.pay(SNAP_TOKEN)` selama token belum expire.
3. **Membuat ulang Snap token untuk order_id yang sama** HANYA berlaku sebelum customer
   memilih payment method ("order_id not yet utilized"): token baru dibuat, **token lama &
   redirect URL lama TIDAK AKTIF lagi**. Setelah customer memilih/mengonfirmasi payment
   method (transaksi `pending`) atau sudah bayar → API error
   `transaction_details.order_id sudah digunakan`.
4. **Rekomendasi resmi untuk multi-attempt**: relasi one-to-many (internal order → banyak
   Midtrans order_id dengan suffix, mis. `web-order-321-{timestamp}`).

## STEP 6 — MAPPING CALLBACK

- Signature Midtrans: `sha512(orderId + statusCode + grossAmount + serverKey)`
  (`lib/services/payment/verifySignature.ts`).
- Uji: kirim notification `pending` asli (tertanda SHA512, order_id `DJ-20260815-FIAN7EZC`,
  status_code 201, gross `35499.00`, transaction_id `92c1d7bc-...`) ke `/api/payment/callback`
  → **HTTP 422** `{"success":false,"orderId":"...","paymentStatus":"pending","message":"Invalid status transition: pending → pending"}`.
  → Membuktikan lookup callback **murni oleh `notification.order_id` → `orders.order_id`**
  (`findByOrderId`); `notification.transaction_id` hanya disimpan ke `orders.transaction_id`
  pada transisi VALID.
- Uji idempotensi: 1 POST = tepat 1 audit entry (kontroll: before 4 → after 1s 5 → after 13s 5).
- Fakta operasional (bonus): **Midtrans SEDANG mengirim notification secara live ke DB ini**
  — bukti: order C menerima 2 `callback.invalid` (16:31:51/52) padahal hanya 2 POST manual
  (16:31:05/43); order D menerima notification `capture` (16:38:31) yang mengubah
  `pending→paid`. Karena `NEXT_PUBLIC_SITE_URL=localhost:3000` (tidak bisa dijangkau
  Midtrans), berarti ada forwarding eksternal (instance deploy / tunnel) yang berbagi
  Supabase DB yang sama. Tidak mengubah kesimpulan, hanya dicatat.
- `DJ-20260815-NNVTIKQW` (order WO 10.14 era) mengonfirmasi pola yang sama: QRIS dibuat,
  `pending→expired` via callback, auto-cancel `payment_expired` — alur expire berjalan otomatis.

## KONSEKUENSI DESAIN UNTUK "RESUME → TETAP ORDER A"

### OPTION A — Reuse Snap token (RECOMMENDED untuk alur resume saat ini)
- Simpan identity order (bukan cuma data form): `orderId` + Snap token (`orders.transaction_id`)
  + waktu pembuatan token.
- Resume: panggil `window.snap.pay(token)` (atau buka `redirectUrl`) langsung dari
  `CartDrawer`/halaman resume. Tidak melewati `/checkout` generate order baru.
- **Tidak mengubah schema DB, mapping callback, ataupun API contract.**
- Guard: hanya izinkan resume saat `payment_status ∈ {unpaid, pending}`. Bila token sudah
  expire (>24 jam sejak dibuat) → keputusan lanjut: coba re-create token untuk order_id sama
  (valid selama order_id "belum terutilisasi"); jika sudah `pending`/`paid` → blokir resume.
- Risiko yang didokumentasikan: token tersimpan bisa stale bila ada token lain dibuat di
  luar aplikasi (kasus S1 vs S2 pada order C — S2 dibuat manual di luar app). Di alur
  normal aplikasi hanya ada 1 token per order, sehingga aman.

### OPTION B — Snap token baru untuk order_id sama
- Hanya valid sebelum payment method dipilih; membatalkan token lama; gagal saat transaksi
  sudah `pending` (error `order_id sudah digunakan`). **Tidak cocok** sebagai mekanisme
  resume umum.

### OPTION C — One-to-many order_id bersuffix (rekomendasi resmi Midtrans untuk multi-attempt)
- Internal order ↔ banyak Midtrans `order_id` (`internal-order-{timestamp}`). Paling kuat
  untuk retry penuh, tetapi butuh: tabel/kolom baru untuk relasi, **perubahan mapping
  callback** (`notification.order_id` ≠ internal `orders.order_id`), dan perubahan saat
  menyimpan `transaction_id` (multi). Paling mahal; tidak diperlukan jika resume cukup
  memakai token lama.

## Keterbatasan & Catatan

- Eksperimen sandbox dengan kartu uji; status transaksi & ttl (24h token, 15m QRIS)
  sesuai konfigurasi sandbox default.
- Order C `DJ-20260815-FIAN7EZC` akan auto-expire (QRIS expiry `2026-08-15 23:46:01`)
  → callback `expire` → status `expired` + auto-cancel (seperti `NNVTIKQW`). Ini bukti
  tambahan, bukan degradasi.
- Anomali "4 callback untuk 2 POST" sudah dijelaskan (delivery live Midtrans, bukan
  double-processing — terbukti uji idempotensi).
- Tidak ada kode diubah. Tidak ada commit/push/deploy. Order A/B/C/D dibiarkan sebagai
  bukti. Artefak eksperimen tersimpan di luar repo
  (`C:\Users\hp\AppData\Local\Temp\opencode\wo1015\`).

## Decision

**ANALISIS SELESAI.** Mekanisme resume yang benar untuk "tetap menggunakan Order A"
adalah **OPTION A: reuse Snap token (`window.snap.pay`)** — resmi didukung, teruji
end-to-end sampai `paid`, tanpa perubahan schema/mapping/API. OPTION B dibatasi kondisi
"belum pilih metode bayar". OPTION C adalah cadangan jika kelak mau multi-attempt penuh.
