# WO 10.14 — Resume Existing Order / Duplicate Order Prevention (AUDIT)

## Ringkasan / Conclusion

Duplikat order TERKONFIRMASI dan TEREPRODUKSI.

Satu checkout/resume menghasilkan **2 record order** dengan data pelanggan & alamat identik
tetapi `order_id` dan `transaction_id` berbeda. Penyebab: alur "Lanjutkan Pembayaran"
tidak pernah melanjutkan order yang sama — setiap mount `/checkout` menghasilkan
`orderId` BARU (client-side), lalu `/api/payment/create` selalu INSERT order baru.

Tidak ada kode yang diubah (sesuai instruksi: audit dulu). Laporan ini berisi
bukti reproduksi, jejak kode (STEP 2–3), definisi dua alur (STEP 4), dan arah desain.

## STEP 2 — JEJAK GENERASI ORDER ID

| # | Pertanyaan | Jawaban (dari source code) |
| --- | --- | --- |
| 1 | Di mana orderId dibuat? | Client-side di `components/checkout/CheckoutForm.tsx:24` → `useMemo(() => buildOrderId(), [])`; format `DJ-YYYYMMDD-XXXXXXXX` dihasilkan `lib/order.ts:1-15` via `Math.random`. |
| 2 | Apakah orderId selalu dibuat client-side? | YA. Server hanya MENERIMA `orderId` dari request body (`app/api/payment/create/route.ts:15`), memvalidasi panjang ≤ 50, dan menolak jika duplikat (409 `ORDER_ID_EXISTS`). Server tidak pernah meng-generate. |
| 3 | Saat resume, apakah original orderId dipertahankan? | TIDAK. `CheckoutState` (`types/checkout.ts`) tidak punya field `orderId`. Restore WO 10.13 (`lib/checkout/restoreOrder.ts`, `CheckoutProvider.tsx`) hanya mengisi `customerInfo`/`shippingAddress`/courier/service/fee — bukan orderId. Setiap mount form → orderId baru. |
| 4 | Apakah API payment/create menerima existing orderId? | Menerima secara teknis, TAPI `OrderService.createDraft` menolak orderId yang sudah ada (`order.service.ts:33-36` → `ORDER_ID_EXISTS` → HTTP 409). Tidak ada jalur "perbarui order lama". |
| 5 | Apakah server selalu insert order baru? | YA. `createDraft` selalu memanggil `OrderRepository.insert` (`order.repository.ts:306-336`) → baris baru + `access_token: crypto.randomUUID()` baru. |
| 6 | Apakah existing order pernah di-update? | Order hanya di-update oleh: `confirmPayment` (status UNPAID→PENDING + `transaction_id` = Snap token) dan `processCallback` (status + `transaction_id` Midtrans + `payment_method`). Tidak pernah ada update identitas/data checkout order lama pada alur resume. |

**Inti masalah STEP 2:** identitas order (orderId) adalah milik form/klien, bukan milik
alur resume. Resume mengembalikan DATA, bukan IDENTITAS order.

## STEP 3 — JEJAK MIDTRANS TRANSACTION ID

| # | Pertanyaan | Jawaban (source + evidence) |
| --- | --- | --- |
| 1 | Apakah original transaction_id disimpan? | YA. `orders.transaction_id` di-set ke Snap token oleh `confirmPayment` (`order.service.ts:100-121`); lalu saat callback di-overwrite dengan `notification.transaction_id` (`order.service.ts:239`). |
| 2 | Saat resume, apakah transaction_id lama dipakai? | TIDAK. Resume via `/checkout` → order baru → Snap token baru. `transaction_id` lama tidak pernah dibaca untuk melanjutkan pembayaran. |
| 3 | Apakah Snap transaction selalu dibuat baru? | YA. `createSnapTransaction` (`lib/services/payment/createSnap.ts:64-170`) selalu memanggil `snap.createTransaction(payload)` → token baru setiap kali. |
| 4 | Apakah Midtrans transaction ID harus sama untuk resume? | Untuk MELANJUTKAN Snap yang sama, token lama bisa dipakai ulang via `window.snap.pay(token)`. **Tetapi aplikasi ini TIDAK punya jalur itu sama sekali** — hasil grep `snap.pay|window.snap` = 0 hasil di seluruh codebase. Satu-satunya "Lanjutkan Pembayaran" (`components/cart/CartDrawer.tsx:153-159`) hanyalah `<Link href="/checkout">` biasa. |
| 5 | Apa yang dilakukan jika transaction lama masih pending? | TIDAK ADA. Order lama dibiarkan `pending`; Snap token lama akan di-expire Midtrans (±24 jam) → callback `expire` → order menjadi `expired` + auto-cancel (`order.service.ts:243-260`). Selama interval itu order A dan B sama-sama pending (double-count). |

**Inti masalah STEP 3:** sistem hanya tahu cara "mulai transaksi baru", tidak tahu cara
"lanjutkan transaksi yang ada". Tidak ada mekanisme re-issue token untuk order yang sama.

## STEP 4 — DUA ALUR YANG HARUS DIBEDAKAN

### A. NEW CHECKOUT (tidak ada order yang bisa dilanjutkan)
```
Cart → /checkout (form kosong)
  → Buat Pesanan → POST /api/payment/create { orderId: BARU }
  → createDraft  → INSERT order baru (UNPAID, access_token baru)
  → createSnapTransaction → token baru
  → confirmPayment → status PENDING + transaction_id = token
  → redirect Midtrans
```
Ini BENAR dan tidak perlu diubah.

### B. RESUME CHECKOUT (guest kembali, ada order pending/unpaid)
**Kondisi saat ini (BUG):** alur B identik dengan alur A → orderId baru → order baru (duplikat).
```
CartDrawer "Lanjutkan Pembayaran" → /checkout
  → form terisi (WO 10.13) TAPI orderId BARU
  → Buat Pesanan → POST /api/payment/create { orderId: BARU }   ← duplicate
  → INSERT order B (duplikat dari A)
```

**Alur yang diharapkan (desain yang diusulkan — BELUM diimplementasikan):**
```
/checkout (mount) → deteksi order resumable {orderId A, accessToken A} (djaemo-last-order)
  → form terisi, dan orderId yang dipakai = A (BUKAN generate baru)
  → Buat Pesanan → POST /api/payment/create { orderId: A }
  → createDraft MENEMUKAN order A yang sudah ada & resumable →
      jalur "resume": UPDATE/refresh (data + totalAmount) atau re-issue Snap token untuk A
      (tidak INSERT baru)
  → redirect Midtrans (token A — lama dipakai ulang, atau token baru untuk order A)
```
Akses kontrol tetap berbasis `access_token` (order A hanya bisa dilanjutkan dengan
token A). Order `paid`/`failed`/`expired` tidak boleh di-resume.

## Dampak Bisnis (dikonfirmasi lewat bukti)

- **Monthly sales recap / order count / revenue aggregation:** A dan B keduanya `pending`
  dengan `total_amount` 35499 → double-count selama keduanya pending.
- **Customer order history:** customer 130 tercatat 2 order untuk 1 checkout.
- **Payment reconciliation:** 2 Snap transaction dibuat untuk 1 produk/destinasi; jika
  keduanya dibayar → 2× pendapatan & 2× stok (stok dipotong saat confirm, bukan create).
- **Shipment:** salah satu dari A/B bisa ter-shipment oleh admin karena tampil sebagai
  order terpisah.
- **Audit trail:** 2× `order.created` + 2× `snap.created` untuk 1 keputusan checkout.

## Arah Desain (opsi, menunggu keputusan Tech Lead/PO — TIDAK diimplementasikan di audit ini)

1. **Resume identity:** simpan `orderId` (bukan hanya data) sebagai bagian dari state
   resume; saat "Buat Pesanan" pada order yang masih resumable, kirim `orderId` lama.
2. **Server guard:** `createDraft` — jika orderId sudah ada dan status resumable
   (`unpaid`/`pending`), jalankan jalur update/re-issue, bukan throw 409. Jika status
   terminal (`paid`/`failed`/`expired`), tolak (409) agar tidak membajak order lain.
3. **Midtrans:** keputusan apakah resume memakai token lama (`window.snap.pay`) atau
   membuat Snap token baru untuk order yang sama — perlu konfirmasi perilaku provider
   (sandbox test) sebelum implementasi.
4. **Cadangan:** jika resume tidak dikehendaki membuat transaksi baru sama sekali,
   alternative adalah tombol "Lanjutkan Pembayaran" yang benar-benar melanjutkan Snap
   lama (tanpa melewati `/checkout`).

## Decision

**AUDIT SELESAI — READY FOR REVIEW.** Duplikat terbukti (STEP 1), akar masalah
teridentifikasi (STEP 2: identitas order tidak di-resume; STEP 3: tidak ada jalur
lanjutkan transaksi), dan dua alur (NEW vs RESUME) telah didefinisikan (STEP 4).
Implementasi perbaikan menunggu persetujuan desain (opsi 1–4) sebelum coding.
