# WO 10.16 — True Payment Resume & Duplicate Order Prevention (IMPLEMENTATION)

## Ringkasan / Conclusion

Flow **Create Order → Payment → kembali → Lanjutkan Pembayaran** diperbaiki:

- Resume memakai **order yang sama** (orderId + accessToken + Snap token lama).
- **Tidak ada** order duplikat.
- **Tidak ada** Snap transaction duplikat.
- Callback Midtrans tetap masuk ke order yang sama (mapping `notification.order_id`).
- Monthly recap melihat **satu purchase = satu order**.

Pendekatan sesuai keputusan WO 10.15 (OPTION A — reuse Snap token): resume TIDAK lagi
melewati `/api/payment/create`; ia mem-fetch ulang order via
`GET /api/orders/{id}?token=...` (kini mengembalikan `transaction_id` = Snap token untuk
order resumable) lalu mengarahkan browser ke redirect URL token yang sama.

## STEP 2 — DEFINE RESUME IDENTITY

Identitas resume = **`{ orderId, accessToken, Snap token }`** (bukan PII seperti nama/email/
telepon/total/customer_id):

- Ditambahkan `CheckoutResume { orderId, accessToken, token, redirectUrl }` di
  `types/checkout.ts` + field `state.resume` + action `SET_RESUME`.
- `CheckoutProvider` mengisi `resume` dari hasil `GET /api/orders/{id}?token=...` ketika
  `isResumableOrder(payment_status)` dan `transaction_id` ada.
- Label tombol submit berubah: "Lanjutkan Pembayaran" saat ada resume, "Buat Pesanan" saat fresh.
- PII TIDAK dipakai sebagai kunci resume — hanya orderId + accessToken (authorization) + token.

## STEP 3 — DETERMINE TOKEN SOURCE

- `orders.transaction_id` untuk order pending berisi Snap token (ditetapkan `confirmPayment`,
  hanya di-overwrite oleh callback pada transisi valid).
- `app/api/orders/[id]/route.ts`: `transaction_id` ditambahkan ke `FULL_FIELDS`.
  - `?token=<valid access_token>` → 200, data lengkap + `transaction_id` (Snap token).
  - `?token=<invalid>` → **403**.
  - tanpa token → 200, hanya field tracking **tanpa** `transaction_id` (tidak expose publik).
- Resume helper baru `lib/checkout/resumeOrder.ts`:
  - `decideResume()` — baca `djaemo-last-order` (orderId+accessToken), validasi status storage,
    fetch `GET /api/orders/{id}?token=...`, cek `isResumableOrder` + token ada → kembalikan
    `{ kind: "resume", orderId, redirectUrl }` atau `{ kind: "none" }`.
  - `buildSnapRedirectUrl(token)` — `https://app.(sandbox.)midtrans.com/snap/v4/redirection/{token}`.

## BREAKING CHANGES

None. API contract `/api/orders/[id]` hanya menambah field `transaction_id` pada respons

callback, admin, tracking) tidak tersentuh.

## REMAINING RISKS

1. **Token expiry:** Snap token default ±24 jam. Jika token kadaluarsa, resume membuka
   halaman Snap yang menolak; per rule #9 tidak dibuat token baru untuk order pending.
   (Perilaku ini dibiarkan sesuai scope; bisa jadi work order lanjutan untuk expired order.)
2. **Stale storage:** jika `djaemo-last-order` menunjukkan status resumable tetapi order
   sudah terminal di server, server authoritative (tidak resume, fallback fresh checkout).
3. **Edit data pada resume:** form yang ke-restore TIDAK mengubah data order lama saat
   resume (resume = bayar ulang order yang sama apa adanya). Mengubah data/total order yang
   sudah punya Snap transaction di luar scope.
4. **Double-click drawer:** tombol resume punya guard `resuming` (disabled sementara).
