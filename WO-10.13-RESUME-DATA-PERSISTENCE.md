# WO 10.13 — Checkout Resume Data Persistence

## Ringkasan / Conclusion

Bug "data checkout yang sudah diisi hilang saat pelanggan kembali" sudah diperbaiki.
Root cause bukan karena data tidak disimpan, melainkan karena tidak ada mekanisme yang
memuat ulang data dari database ke form checkout (`/checkout`) saat pelanggan kembali
dan memilih "Lanjutkan Pembayaran".

Perbaikan: `/checkout` sekarang melakukan hidrasi ulang (restore) dari order di database
menggunakan `access_token` yang tersimpan di localStorage. Valid untuk order berstatus
`unpaid`/`pending`. Token invalid / order tidak ditemukan → form tetap kosong (tidak ada
kebocoran data, API sudah 403).

Catatan terkait: DB telah dibersihkan (SQL WO 10.12B terlihat sudah dieksekusi — orders,
order_items, customers, audit_logs, webhook_debug_logs, notification_log, promos,
promo_products = 0; master data stock_movements 36, products 3, product_images 15,
profiles 1 tetap utuh). Reproduksi WO 10.13 dibuat dengan order test baru:
`DJ-20260815-AV82FIEQ` (status `pending`, sengaja dibiarkan sebagai artefak test).

## Root Cause

- Kategori: **B (data disimpan tetapi tidak diambil ulang)** dengan aspek C (data yang
  sudah diambil oleh halaman sukses hanya untuk tampilan, tidak di-set ke state checkout).
- Alur saat bug:
  1. Guest isi data → POST `/api/payment/create` → `OrderService.createDraft`
     menyimpan snapshot lengkap ke `orders` (`customer_name`, `customer_phone`,
     `customer_email`, `shipping_address` gabungan, `destination`, `postal_code`,
     `destination_area_id`, `courier_company`, `courier_type`, `shipping_cost`, `notes`,
     `access_token`) + `order_items` + upsert `customers`.
  2. `CheckoutForm` menulis localStorage `djaemo-last-order` TANPA `accessToken`.
  3. Guest ke Midtrans, kembali, klik "Lanjutkan Pembayaran" (CartDrawer =
     `<Link href="/checkout">`, tanpa order/token).
  4. `/checkout` memuat `CheckoutProvider` dengan state awal KOSONG — tidak ada kode yang
     memanggil `GET /api/orders/[id]?token=` untuk mengisi ulang state. → Data hilang.

## Current Flow (sebelum) vs Expected Flow (sesudah)

**Sebelum (bug):**
```
/checkout → CheckoutProvider state kosong → form kosong
```

**Sesudah (fix):**
```
/checkout (mount) →
  baca djaemo-last-order {orderId, accessToken} →
  GET /api/orders/{orderId}?token={accessToken} (authorized) →
  jika payment_status ∈ {unpaid, pending} →
  restore ke state (customerInfo, shippingAddress, courier, service, fee) →
  form terisi; AreaSelect menampilkan nilai restore; kurir otomatis ter-highlight
jika token invalid/order tidak ada/status paid → form tetap kosong (fresh checkout)
```

## Remaining Risks

1. Setelah restore, jika pelanggan ingin MENGGANTI kota/kecamatan/kelurahan tanpa
   mengganti provinsi, dropdown dependen tidak punya id area (`provinceId`/`regencyId`/
   `districtId` tidak disimpan di DB), sehingga saran hasil ketik bisa kosong. Solusi
   jalan: pilih ulang provinsi dulu (meng-reset rantai id). Ini bukan kehilangan data.
2. `areaId` di DB bisa kosong (tergantung request asal) — restore tetap berjalan via
   parsing `shipping_address`.
3. Order test `DJ-20260815-AV82FIEQ` dibiarkan di DB sebagai artefak; akan ikut terbersihkan
   pada proses clean-up berikutnya.
4. Scope restore dibatasi status `unpaid`/`pending` (skenario WO). Order `failed`/`expired`
   tidak di-restore otomatis (halaman sukses sudah mengarahkan ke "Checkout Ulang").
